# v2.00 Overview — Factory Complexity & Content Scalability

## Implementation gate

Status: **Planned — blocked on v1.00 MVP acceptance**. Complete v1 Phases 7–10, verify deployment and get owner approval of visuals/playability before implementing this phase. Preserve the existing historical v2.00 branch; integrate the accepted v1 baseline without rewriting history. Existing nested RNG, themed cubes, category inventory and alternate sellers are v1 foundations, not evidence that this phase is complete.

## Version Purpose

Turn a validated single-route factory into a deeper optimization sandbox without sacrificing usability or maintainability.

## Primary Validation Question

> **Can players build meaningfully different factories rather than converge on one obvious line?**

## Scalability Objective

Support multiple production lines, routing, split/merge logic, richer machine behavior, and a larger content library through modular systems.

## Player-Facing Objective

Players gain:

- multiple routes
- branch decisions
- splitters and mergers
- deeper throughput tradeoffs
- stronger layout tools
- clearer production statistics
- more machine interactions
- larger but still manageable factories

## Architecture Objective

- node/graph or equivalent logistics representation
- reusable logistics nodes
- behavior composition for machines
- versioned layout serializer
- instrumentation for machine and route cost
- content configuration that avoids central-code edits

## Planned Phases

1. Logistics Graph Foundation
2. Branching, Splitters & Mergers
3. Machine Framework Expansion
4. Advanced Building, Inventory & Stats
5. Balance, Performance & v2 Validation

## Expected Content

Add only enough machines to create strategy diversity. Keep the accepted v1 catalog (80 droppers/sellers plus upgraders). Add only mechanics that create routing decisions; raw variant count is not a v2 goal.

## Analytics Goals

- layout diversity
- branch count
- splitter/merger usage
- route congestion
- machine pair/order frequency
- underused machines
- dominant strategies
- rebuild frequency
- performance by layout complexity

## Economy Considerations

Do not add new currencies merely because scope is larger.

Revisit roll pools and acquisition agency if a larger machine library makes targeted experimentation too difficult.

## Security Risks

- invalid graph connections
- duplication through split/merge edge cases
- stale layout transactions
- build-tool replication abuse
- save corruption from richer layouts

## Performance Risks

- branch fanout
- duplicated items
- graph traversal cost
- more simultaneous machines
- more visible effects
- larger serialized layouts

## Deferred Systems

- trading
- clans
- broad social progression
- seasonal events
- advanced prestige
- marketplace

## Exit Criteria

- multiple-line layouts are reliable
- split/merge behavior is deterministic
- adding a normal machine rarely requires core-system edits
- building remains usable on mobile
- no dominant layout invalidates most content
- performance remains acceptable at v2 factory caps
- analytics demonstrate meaningful layout diversity
